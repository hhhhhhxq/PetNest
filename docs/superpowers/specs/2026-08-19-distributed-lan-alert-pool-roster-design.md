# 分布式局域网预警池成员名单设计规格

日期：2026-08-19

## 1. 背景

PetNest 当前内置一个固定“局域网预警组”。用户可以自行加入或退出，但页面成员数来自本机实时发现的 `LanPeer` 集合。处于同一公司网络但不同 IPv4 子网或 VLAN 的设备，即使能够通过路由单播通信，也收不到彼此的广播发现包。因此不同设备可能看到不同的成员数，跨网段成员仍需要逐台输入 IP。

本功能把预警组改造为一个固定、无群主、无中心服务器的“局域网预警池”。每台设备持久化一份成员名单；设备建立任意直接连接后比较并合并名单。两个广播域之间只需任意一对设备建立一次桥接，之后加入、退出和地址变化会通过已有成员持续传播，不再要求所有成员两两添加。

## 2. 目标

- 继续只提供一个固定预警池，不增加群组创建、群名、群主或管理员。
- 所有兼容客户端都可自行加入和退出。
- 每台设备持久化完整成员名单，不依赖唯一协调者或服务器。
- 同网段使用现有广播自动发现；跨网段使用已保存端点自动重连。
- 任意两台已知成员连接时自动比较名单，只传输缺少或过期的记录。
- 支持断线期间的加入、退出和地址变化，恢复连接后自动补偿同步。
- 页面区分“已加入成员数”“当前在线数”“当前可发送数”。
- 发送聊天和危险预警时只选择已加入、在线并已直接验证的设备。
- 保持现有预警 ack、重试、去重、限流、全屏动效和可选文案行为。
- 不使用 Firebase、固定内网服务器、写死 IP 或临时协调者选举。

## 3. 非目标

- 不保证两个从未建立任何联系且广播完全隔离的网段能凭空互相发现。
- 不提供多个预警池、邀请链接、群号、群主、踢人或全局黑名单。
- 不在第一版引入账号、设备公钥、数字签名或端到端加密。
- 不使用成员名单中未经直接验证的端点发送聊天或预警。
- 不把局域网开放池扩展为互联网群聊。
- 不依赖路由器跨 VLAN 广播转发。

## 4. 用户体验

互动页面固定显示：

```text
局域网预警池

已加入 8 人
当前在线 6 人
当前可发送 5 人

小林    在线 · 可发送
小陈    在线 · 正在验证
小周    离线
```

用户只有两个成员操作：

- `加入预警池`
- `退出预警池`

没有创建者、群主或协调者展示。内部名单交换、跨网段桥接和冲突合并对用户透明。

当本机尚未加入时仍可看到已知池成员，但不能发送或接收预警池聊天和危险预警。退出时继续保留其他成员名单，以便以后重新加入后恢复同步；本机退出记录必须传播，避免被旧名单重新加入。

## 5. 数据模型

### 5.1 `PoolMemberRecord`

每个设备只产生和更新属于自己的记录：

```text
device_id           稳定设备 ID
display_name        当前昵称
state               joined 或 left
revision            本设备成员记录的递增修改序号
ip_address          最近一次声明的 IPv4
port                PetNest 服务端口
protocol_version    名单同步协议版本
```

`revision` 不是软件版本，也不是全池版本。它只表示同一 `device_id` 的记录修改次数：

```text
revision 1：首次加入
revision 2：昵称或端点变化
revision 3：退出
revision 4：重新加入
```

每台设备把自己的 `revision` 持久化。加入、退出、昵称变化或已验证端点变化时递增。其他设备只能转发该记录，不能代替其递增。

### 5.2 `PoolRoster`

名单是：

```text
device_id → PoolMemberRecord
```

最多保存 256 个设备记录。`left` 记录作为 tombstone 保留，不参与成员数显示，但不立即删除，避免长期离线设备携带旧 `joined` 记录回来后让已退出成员复活。

### 5.3 在线与验证状态

以下状态只由本机运行时计算，不作为权威成员记录传播：

- `known`：名单中存在 `joined` 记录；
- `online`：最近收到该设备心跳；
- `verified`：已与该设备完成 device ID、IP、UDP 来源端口和广告端口一致的直接握手；
- `reachable`：当前存在可用直连端点。

成员总数统计 `joined` 记录；在线数统计最近心跳；可发送数统计 `joined + online + verified + reachable`。

## 6. 名单合并规则

合并以每个 `device_id` 为单位：

1. 本地没有该记录：接受远端记录。
2. 远端 `revision` 更大：远端覆盖本地。
3. 本地 `revision` 更大：保留本地，并在响应中向对方补发本地记录。
4. `revision` 相同且内容一致：不操作。
5. `revision` 相同但内容不同：标记冲突，不随机覆盖；要求与记录所属设备直接握手，直接来源的自有记录胜出。

从第三方名单中获得的新记录可以加入“已知成员”集合，但其端点在直接握手成功前保持未验证，不能成为聊天或预警收件人。

## 7. 同步协议

### 7.1 UDP 心跳

在现有 UDP `18487` 上增加 `pool_heartbeat`：

```text
pool_id
sender_device_id
sender 自有 PoolMemberRecord
roster_digest
record_count
```

用途：

- 宣布本机在线；
- 传播本机最新加入或退出状态；
- 快速判断双方名单是否可能不同；
- 触发后续 TCP 名单校对。

心跳不携带完整名单，继续受现有包大小和速率限制。

### 7.2 TCP 名单校对

现有 TCP `18487` 帧从“仅聊天帧”扩展为带 `kind` 的通用帧。新增：

- `pool_summary`：最多 256 组 `device_id + revision`；
- `pool_records`：响应对方缺少或版本落后的具体记录。

流程：

```text
A 与 D 连接
  ↓
交换 pool_summary
  ↓
计算双方缺失或过期的 device_id
  ↓
双向发送 pool_records
  ↓
合并并原子保存
  ↓
如本地名单变化，向少量其他已知成员传播摘要
```

完整名单不通过 UDP 广播，避免网络放大和超大数据报。

### 7.3 同步时机

- 应用启动；
- 发现新设备；
- 手动 IP 或保存端点连接成功；
- 本机加入或退出；
- 本机昵称或已验证端点变化；
- 收到不同 `roster_digest`；
- 每 30 秒随机选择最多 3 个可达成员做一次校对。

周期校对不连接全部成员，避免人数增长后形成平方级网络流量。

## 8. 跨网段传播流程

初始状态：

```text
101 网段：A
106 网段：D
```

A 与 D 通过一次 IP 连接建立桥接，双方保存彼此端点并持续重连。

之后 B 在 101 网段首次加入：

1. B 通过本地广播发现 A。
2. B 生成自己的 `joined revision 1` 记录。
3. A 与 B 校对名单，A 获得 B。
4. A 下次与 D 校对时发送 B 的记录。
5. D 保存 B，并向 106 网段其他已知成员传播摘要。

若 D 当时离线，A 保存 B 的记录；D 恢复后通过摘要差异补收。E、F 以后经 D 加入时采用相同流程。名单同步不是 A、D 建桥时的一次性复制，而是所有后续连接都会执行的持续校对。

如果 A 和 D 都离线，两个网段可以暂时各自更新名单；任意桥接成员恢复后按 `revision` 合并。若一个全新设备第一次运行时，本地没有任何已同步成员在线，也没有可达入口，则只能等待成员上线或输入一个入口 IP。

## 9. 本地存储

新增独立 `lan-alert-pool-roster.json`，与 `settings.json` 同目录。格式包含：

- schema version；
- 本机自己的最新 revision；
- `device_id → PoolMemberRecord`；
- 最近验证端点只作为重连线索，不自动视为在线。

写入沿用 `KnownLanPeerRegistry` 的临时文件、`fsync`、原子替换、损坏备份和写保护模式。名单损坏不能阻止桌宠启动；本机自己的加入状态仍可从现有设置恢复并生成新的自有记录。

## 10. 与现有逻辑的关系

- `KnownLanPeerRegistry` 继续保存用户手动验证或名单同步后直接验证成功的重连端点。
- `PoolRosterStore` 保存成员关系，不代替端点注册表。
- `LanInteractionService` 继续负责 presence、聊天、预警和 ack。
- 新增 `LanPoolSyncService` 负责名单摘要、记录交换、合并和周期校对。
- 互动页面不再通过当前 `_peers` 推断成员总数，而是读取 `PoolRosterStore`；在线和可发送状态再与实时 peer 表关联。
- 现有 `lan_alert_group_joined` 设置迁移为本机自有成员记录的 `state`，之后保持二者一致。

旧客户端没有名单同步协议：

- 仍可使用普通局域网发现、私聊和普通群聊；
- 不计入分布式预警池成员总数；
- 不接收新名单同步消息；
- 新客户端不得把旧客户端的临时 presence 当作持久成员记录。

## 11. 安全与资源边界

第一版沿用“可信局域网”边界，不引入账号或数字签名，但必须：

- 只有直接握手验证成功的端点可以接收聊天和预警；
- 第三方转发记录不能直接把端点标为 verified；
- 每个名单最多 256 条记录；
- summary 和 records 严格限制字段、长度、条目数和总字节数；
- 同一来源的心跳与名单请求限流；
- 不接受记录替其他 `device_id` 随意提高 revision 的行为作为直接验证结果；
- revision 相同但内容冲突时不静默覆盖；
- 本地屏蔽、预警限流、消息去重和过期校验继续有效。

开放池意味着任何能与现有成员建立连接的兼容 PetNest 都可以加入。第一版不提供全局踢人或防 Sybil 保证；如果以后需要受控成员资格，再增加群号或设备签名，不改变名单同步的主体结构。

## 12. 错误处理

- UDP 心跳丢失：等待后续心跳或周期 TCP 校对。
- TCP 名单校对失败：保留本地名单，下次连接重试。
- 部分网段断开：各自继续更新，恢复后按 revision 合并。
- 对方发送超限或非法快照：拒绝整帧，不留下半份名单。
- 存储损坏：备份损坏文件，从本机设置和已验证伙伴逐步重建。
- 同 revision 冲突：显示调试日志并等待记录所属设备直接上线解决。
- 成员端点变化：只有新端点直接握手验证后才更新可发送状态。

## 13. 测试策略

### 单元测试

- 自有 revision 在加入、退出、昵称和端点变化时递增；
- 高 revision 覆盖低 revision；
- `left` tombstone 阻止旧 joined 记录复活；
- 相同 revision 冲突不静默覆盖；
- roster schema、条目数、字段和原子存储；
- heartbeat、summary、records 编解码和大小限制；
- 第三方端点在直接验证前不可发送；
- 已加入、在线、可发送三个计数分别正确。

### 集成测试

模拟 A、D 先桥接，随后 B、E 才加入：

```text
初始：A、D
B 经 A 加入
E 经 D 加入
最终四台设备名单一致：A、B、D、E
```

再覆盖：

- D 在 B 加入时离线，恢复后补收 B；
- 101、106 两侧同时新增成员，恢复桥接后合并；
- A 退出后旧 joined 记录不能复活；
- 桥接端点变化后重新验证并继续同步；
- 旧客户端忽略新消息且普通聊天不回归；
- 256 人边界和恶意超大快照被拒绝。

### 回归测试

运行完整 pytest 套件，并人工使用两个本地服务实例模拟不同子网端点；确认现有普通群聊、预警 ack、全屏动效、设置迁移和已保存伙伴重连保持正常。

## 14. 验收标准

- 固定预警池无创建者、群主、群名和协调者 UI。
- 每台兼容客户端都可自行加入和退出。
- A、D 建桥后，之后经任一侧本地成员加入的 B、C、E、F 会最终传播到另一侧。
- 对侧离线期间的成员变化在恢复连接后补偿同步。
- 所有已同步设备最终拥有相同 `device_id → state/revision` 名单。
- 页面分别显示已加入、在线和可发送人数。
- 未直接验证的第三方端点不会收到聊天或危险预警。
- 无 Firebase、固定服务器、写死 IP 和协调者选举依赖。
- 两个完全隔离且从未桥接的网段不会被错误宣称为已同步。
