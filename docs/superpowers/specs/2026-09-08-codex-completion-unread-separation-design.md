# Codex 完成状态与待查看计数分离设计

## 问题

PetNest 当前把每个 `Stop` 事件直接标记为未读。Codex 的顶层任务、前台已经查看的任务和子代理都会产生 `Stop`，因此 PetNest 的“待查看”数量会累计所有完成会话，而不是 Codex 当前真实未读的顶层任务数。

实际复现中，PetNest 显示 8 个待查看；同一时刻 Codex 只有 1 个顶层未读。其余 7 个由 3 个子代理完成和 4 个已查看的顶层任务完成组成。

## 目标与不变量

- `Stop` 只表示任务刚完成，用于一次临时完成动画和完成气泡。
- 待查看数量只由经过子代理过滤的 `ThreadUnread` 增加，由 `ThreadRead` 清除。
- 子代理完成不播放 review、不增加待查看，也不遗留 working 状态。
- 子代理的 `PermissionRequest` 和失败状态在任务活动期间继续保留；对应 `Stop` 到达后说明任务已结束，清除提醒但不播放 success。
- 数据库不可用或任务关系尚未写入时，不猜测未读；允许一次短暂完成动画，但不得产生假待查看数量。
- PetNest 启动时恢复当前仍未读的顶层任务，不能因重启把真实数量错误归零。
- Codex 暂时把仍在运行的顶层任务标成 unread 时，不提前计入“待查看”；该任务 `Stop` 后才转为真实待查看。

## 方案比较

1. 只在显示层用 Codex 当前数量覆盖 PetNest 数量：能修正文案，但协调器内部仍保留错误任务，动画和点击目标继续异常。
2. 完全忽略所有子代理 Hook：实现简单，但会漏掉子代理的权限请求和失败提醒。
3. 分离完成与未读，并只过滤子代理 `Stop`：待查看以 Codex 未读为唯一事实来源，同时保留真正需要用户处理的子代理状态。采用此方案。

## 设计

### 任务分类

`CodexSessionLogWatcher` 对外提供现有只读任务分类能力。`CodexLinkCoordinator` 接收可选的批量分类函数，只在处理 `Stop` 时查询当前会话是否为子代理。

- 已确认子代理：移除该会话现有任务状态，记录完成去重信息，不创建 review。
- 已确认顶层任务：创建临时 review，未读标志仅取决于该会话是否已收到 `ThreadUnread`。
- 未知任务：按顶层任务播放临时 review，但未读保持为 false；后续只有 `ThreadUnread` 能增加数量。

查询沿用 `CodexThreadIndex` 的路径校验、只读 SQLite、短超时和 schema 降级规则，不读取对话正文。

### 状态与气泡

顶层 `Stop` 创建 `review_animation_pending=true`、`unread_review=false` 的临时任务。应用在临时 review 期间显示“Codex 任务已完成”气泡并播放 review 动画。

- 动画期间收到 `ThreadUnread`：任务变成真实未读；动画结束后折叠为“N 个待查看”。
- 动画结束仍未收到 `ThreadUnread`：删除临时 review，回到其他活动状态或 idle，气泡消失。
- 收到 `ThreadRead`：删除对应 review 与未读状态。

review 动画期间的完成文案不使用“等待查看”，避免把尚未确认的完成误称为未读。

若运行、等待或失败中的任务先收到 `ThreadUnread`，协调器只保存原始未读事实，不创建 review、不增加展示数量；对应顶层 `Stop` 到达后再把它转成已完成未读。这样 Codex 后台输出导致的活动任务 unread 不会被误称为待查看。

### 子代理 Stop 清理

子代理 `Stop` 不创建完成动画。若此前该子代理的运行事件已进入协调器，则同时移除该子代理的任务和活动轮次，重新聚合剩余顶层/注意状态，防止残留 working。

### 启动恢复

监听器启动时不直接重放全部未读历史，而是把启动瞬间的未读 ID 放入待分类集合。第一次轮询先以最新全局状态剔除已经读掉的 ID，再通过任务索引只恢复仍存在的顶层未读；子代理被丢弃，未知 ID 保留等待后续分类。这样重启后待查看数量仍与 Codex 当前状态一致。

## 测试

- 顶层 `Stop` 后未读数量为 0，但会进入临时 review。
- 临时 review 气泡显示“任务已完成”，动画结束且无 `ThreadUnread` 时消失。
- 顶层 `ThreadUnread` 到达后数量增加，`ThreadRead` 后清除。
- 三个子代理和五个顶层任务完成、只有一个顶层未读时，最终数量严格为 1。
- 子代理 `Stop` 不发布 success，并清除该子代理的 working。
- 子代理 waiting/failed 仍可正常聚合。
- 子代理 waiting/failed 后收到终止 `Stop` 时回到剩余状态或 idle，不发布 success。
- 分类不可用时不增加待查看数量。
- 启动时只恢复当前仍未读的顶层任务，不恢复已读任务和子代理。
- 运行中的顶层任务先收到 `ThreadUnread` 时数量保持不变，`Stop` 后才增加。
