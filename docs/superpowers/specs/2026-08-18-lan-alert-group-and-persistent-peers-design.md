# 局域网预警组与伙伴持久化设计规格

日期：2026-08-18

## 1. 背景

PetNest 已有局域网设备广播发现、手动 IP 连接、点对点互动、局域网群聊和桌宠旁消息气泡。当前局域网设备与手动连接目标都只保存在运行内存中：应用退出后，手动添加的 IP 会丢失；超过 24 秒未收到握手的设备会从在线列表移除。自动发现只向 `255.255.255.255` 发送一次广播，在多网卡环境下可能只经一个接口发出，也无法可靠跨越办公网络中的不同子网或 VLAN。

本功能同时解决两个问题：

1. 用户通过 IP 成功连接一次局域网伙伴后，PetNest 永久保存该伙伴，并在以后启动时自动定向连接。
2. PetNest 提供一个无群主、固定名称的“局域网预警组”。用户自行加入或退出，组内成员可聊天，也可从桌宠右键菜单向当前在线组员发送高优先级危险预警。

## 2. 目标

- 尽量发现本机所有有效 IPv4 接口所在广播域内的 PetNest 设备。
- 支持首次手动输入可互通设备的 IP，之后自动重连，不要求本机也连接对方使用的 Wi-Fi。
- 将实时在线状态、已保存伙伴数据和预警组加入状态分开建模。
- 提供一个所有兼容客户端都天然认识的固定预警频道，不创建群主、邀请和共享成员表。
- 只向当前在线且主动加入预警组的成员发送预警组聊天和危险预警。
- 危险预警使用独立协议、送达确认、一次重试、去重和频率限制。
- 接收端仅在桌宠所在屏幕显示红色半透明警示层，约 1.5 秒闪烁 3 次后自动消失。
- 保持旧客户端的普通设备发现、私聊、局域网群聊和快捷互动可用。

## 3. 非目标

- 不创建多个命名群组、私人群组、群主、管理员、邀请或踢人能力。
- 不扫描用户未明确提供的整个远端子网或地址范围。
- 不依赖 Firebase 远程伙伴链路传输预警组消息。
- 不播放警示音，不向所有显示器同时显示警示层。
- 不为群聊增加跨重启历史、离线消息或服务端存储。
- 不把 PetNest 预警替代为正式的消防、安防或紧急广播系统。
- 不在本期引入密码学设备身份；沿用现有办公局域网信任边界，并增加端点匹配、时效、去重和限流保护。

## 4. 核心模型与职责边界

### 4.1 `LanPeer`

保留现有 `LanPeer` 作为运行时设备快照，表示当前已发现或已握手成功的设备。它可以携带当前连接状态、协议支持情况和本次运行最后一次看到的预警组加入状态，但不直接承担磁盘持久化。

### 4.2 `KnownLanPeerRegistry`

新增轻量的已保存伙伴注册表，独立于普通 `Settings`。注册表只负责定向重连所需的局域网连接数据，不保存本机或远端的预警组成员关系。

每条记录包含：

- `device_id`
- 最近一次验证的显示名称
- 最近一次验证的 IPv4 地址
- UDP/TCP 共用的服务端口
- 注册表格式版本

注册表写入当前用户配置目录，与 `settings.json` 同目录，文件名为 `known-lan-peers.json`。写入使用同目录临时文件和原子替换；损坏文件重命名为带时间戳的备份后，以空注册表继续启动。手动 IP 验证成功后自动保存。用户可通过“更新地址”和“忘记此伙伴”修改或删除记录。

若保存的 IP 回应了不同的 `device_id`，服务不得覆盖原记录，而应将该伙伴标记为地址冲突，提示用户重新验证。若同一 `device_id` 通过正常广播或定向握手出现在新地址，注册表可在验证端点身份后更新最近地址。

### 4.3 固定预警组

预警组是协议约定的系统频道，固定标识为 `lan_alert_group`，固定显示名称为“局域网预警组”。它不是某台设备创建并同步出去的数据对象。

每台设备只保存自己的 `lan_alert_group_joined: bool` 设置，默认值为 `false`。任何设备只能决定自己是否加入，不能替其他设备增加或删除成员。所有已加入成员都可以发送群聊和危险预警。

远端成员状态来自当前握手：在线设备明确报告其加入状态；旧客户端或缺少字段的设备视为不支持；无法连接的已保存伙伴状态为未知。当前运行中刚刚离线的伙伴可以显示最后观察到的状态，但不得把该缓存当成持久化成员表或发送依据。

### 4.4 关联方式

三个概念保持独立：

`已保存伙伴记录 → 负责找到设备`

`实时 LanPeer → 负责当前端点和在线状态`

`远端自行声明已加入 → 负责是否属于预警频道`

发送预警组消息时，只选择当前实时在线、明确支持并声明已加入的 `LanPeer`。手动保存伙伴不会让其加入预警组；加入预警组也不会把对方保存为本机伙伴。

## 5. 设备发现与跨网段重连

### 5.1 多接口广播

发现服务枚举 Qt 返回的网络接口与地址条目，选择满足以下条件的 IPv4 地址：

- 接口同时为 `IsUp` 和 `IsRunning`；
- 不是回环接口；
- 地址不是 `0.0.0.0`、回环地址或 `169.254.0.0/16` 链路本地地址；
- 地址条目具有非空广播地址。

服务向每个唯一广播地址发送 `hello`，并保留一次 `255.255.255.255` 发送作为兼容补充。广播地址去重，单个接口异常不能阻止其他接口发送。当前测试环境中应识别有线接口 `192.168.101.14/24` 并向 `192.168.101.255` 发送；Tailscale 的 `169.254.x.x` 和断开的 WLAN 不计入有效办公网接口。

多接口广播只能扩大本机直接连接广播域内的发现范围。路由器通常不会跨 VLAN 转发广播，因此它不承诺发现所有“可以单播互通”的其他子网。

### 5.2 已保存伙伴定向重连

局域网服务启动后加载全部已保存伙伴，向每条最近 IP/端口发送定向 `hello`，随后使用现有手动伙伴刷新定时器持续续期。定向连接不依赖广播，因此只要网络路由和防火墙允许，即可连接其他可互通子网中的设备。

互动页面对已保存伙伴显示以下状态：

- `正在连接`：启动后尚未收到定向握手结果；
- `已保存 · 在线`：当前端点已验证；
- `已保存 · 离线`：探测超时或后续失联；
- `地址冲突`：保存地址回应了其他设备身份；
- `不支持预警组`：已连接，但握手未包含预警组协议字段。

自动发现且未保存的设备只在在线时显示为“附近 · 在线”，不会形成永久列表。

## 6. 握手与兼容性

现有 `hello` 和 `hello_ack` 顶层增加可选字段：

```json
{
  "alert_group_joined": true
}
```

不得将该状态加入现有 `capabilities` 数组，因为旧版解码器会拒绝不认识的 capability。旧客户端会忽略未知顶层字段，因此仍能发现新版客户端。新版客户端收到缺少字段的旧版握手时，将该设备标记为“不支持预警组”。

旧客户端：

- 页面中没有预警组入口；
- 不能加入或接收预警组群聊与危险预警；
- 仍可使用原有设备发现、私聊、局域网群聊和快捷互动；
- 新版发送端不会把旧客户端列入预警组收件人。

用户加入或退出预警组后，服务立即重新发送广播 `hello`，并向已保存在线伙伴发送定向 `hello`，使状态变化尽快可见。

## 7. 群聊范围

保留现有“局域网群聊”，其收件范围仍为所有当前在线局域网设备。新增“局域网预警组”会话，其收件范围仅为当前在线且明确加入预警组的兼容设备。

聊天模型由布尔 `is_group` 演进为明确的会话范围：

- `direct`
- `lan_room`
- `alert_group`

旧协议中的 `scope: "group"` 继续映射为 `lan_room`；新预警组消息使用 `scope: "alert_group"`。为减少调用方一次性迁移风险，模型可以保留兼容读取属性，但新代码不得再通过单个布尔值决定收件范围。

接收预警组聊天时，本机必须已加入预警组，且发送者当前在线、端点身份匹配并声明已加入。预警组聊天继续使用现有的本次运行内存记录，不增加离线补发。

现有“群聊消息显示宠物气泡”设置同时控制普通局域网群聊和预警组聊天气泡；关闭后消息仍进入本次运行的聊天记录。危险预警不受该气泡设置影响。

## 8. 危险预警协议

危险预警使用独立 UDP 消息，不伪装成聊天文本或普通互动。发送包至少包含：

- 协议版本和 `kind: "danger_alert"`
- 唯一 `alert_id`
- 发送设备 ID 与显示名称
- 目标设备 ID
- 创建时间戳

接收端必须验证：

- 本机当前已加入预警组；
- 目标设备 ID 为本机；
- 发送者存在于当前实时在线设备表；
- 数据包来源地址与已验证端点匹配；
- 发送者明确支持并加入预警组；
- 时间戳在允许的短时窗口内；
- `alert_id` 尚未处理；
- 同一发送者未超过接收限流。

验证通过后，接收端先登记 `alert_id`，再回复 `danger_alert_ack` 并调度警示层。确认包包含 `alert_id`、发送与目标设备 ID。发送端只接受来自预期目标端点的确认。

发送端对未确认成员重试一次；接收端根据 `alert_id` 去重，因此重试不会重复闪屏。等待窗口结束后，发送端汇总实际确认数量，而不是把 UDP 写入成功当作送达成功。

本机发送成功后进入 5 秒冷却；接收端对同一发送者限制为每分钟最多触发 3 次。过期、重复、未知发送者、未入组发送者和目标不匹配的消息静默拒绝并写入调试日志。

## 9. 用户界面

### 9.1 互动页面

“附近设备”区域保留现有“连接电脑 IP”，并在设备列表顶部提供两个固定会话入口：

- `局域网群聊`
- `局域网预警组`

预警组未加入时，右侧显示用途说明、隐私/安全边界和“加入预警组”按钮，不启用聊天编辑器。加入后显示当前在线成员与预警组聊天；退出操作需要确认，完成后立即停止接收预警组聊天和危险预警。

设备行显示来源与状态。手动 IP 验证成功后自动保存；已保存设备提供“更新地址”和“忘记此伙伴”。忘记伙伴只删除本地定向重连信息，不改变对方自行控制的预警组状态。

### 9.2 桌宠右键菜单

右键菜单新增“⚠ 发送危险预警”。菜单项始终可见：

- 本机未加入时，点击后说明需要先加入，并可打开预警组页面；
- 本机已加入但无其他在线成员时，提示“当前没有其他在线成员”，不允许发送；
- 有在线成员时，二次确认框列出本次接收人，并单独显示当前无法连接或状态未知的已保存伙伴；
- 红色“立即发送”按钮执行发送，普通“取消”按钮关闭确认框。

发送者本机不播放全屏警示，只在桌宠旁显示汇总结果：

- `预警已送达 4 人`
- `已送达 4/5，小林未响应`
- `预警组当前无人在线`

## 10. 全屏警示层

新增独立 `DangerAlertOverlay`，不复用下班动画资源播放器。它只负责短时、高优先级、无交互的屏幕警示。

- 使用桌宠窗口中心点选择 `QScreen`，找不到时回退到主屏幕；
- 使用完整 `screen.geometry()`，覆盖任务栏区域；
- 无边框、置顶、透明背景、鼠标穿透、显示时不激活窗口；
- 红色半透明背景在约 1.5 秒内形成 3 个明显峰值，频率不超过约 2 Hz；
- 中央显示“危险靠近”，下方显示“由〈发送者昵称〉发出”；
- 不播放声音，不提供按钮，完成后自动隐藏；
- 若下班全屏动画正在显示，警示层在其上方短暂显示，结束后下班动画继续；
- 相同 `alert_id` 的重试不会重新启动动画。

## 11. 错误处理与生命周期

- 任一广播接口发送失败不影响其他接口。
- 单个预警收件人发送或确认失败不影响其他收件人。
- 服务关闭时清理套接字、重试计时器、确认等待和警示窗口。
- 伙伴注册表损坏时备份损坏文件并继续启动，不拖垮桌宠主流程。
- 保存地址超时后保留伙伴记录并显示离线；用户可以更新地址或忘记伙伴。
- 地址返回错误身份时不自动改绑，防止 DHCP 地址复用导致误认。
- 本机退出预警组后，即使收到延迟数据包也拒绝显示。
- 应用重启后不会恢复旧聊天、未完成的发送或旧预警动画。

## 12. 测试策略

### 12.1 单元测试

- 有效接口筛选、广播地址去重以及链路本地/回环/断开接口排除。
- 注册表原子读写、损坏备份、保存、更新、忘记和身份冲突。
- 设置迁移为 `lan_alert_group_joined = false`。
- 新旧握手包双向兼容和“不支持预警组”识别。
- `direct`、`lan_room`、`alert_group` 编解码和历史隔离。
- 危险预警与确认包的字段校验、时效、端点匹配、去重和限流。
- 预警发送确认、一次重试、部分送达和超时汇总。
- 互动页面的加入、退出、在线、连接中、离线、不支持和地址冲突状态。
- 右键确认框的空组、无人在线、部分离线和冷却状态。
- 警示层的屏幕选择、完整 geometry、窗口 flags、3 次峰值和自动隐藏。

### 12.2 集成测试

使用三个本地 `LanInteractionService` 实例模拟 A、B、C：B 加入、C 未加入，验证预警组聊天和危险预警只到达 B，普通局域网群聊仍到达 B、C。验证确认包、重试去重和发送结果汇总。

模拟手动 IP 伙伴保存、服务重启和定向重连；验证保存伙伴无需再次输入 IP 即可恢复在线。模拟保存地址返回不同设备 ID，确认原记录未被覆盖。

### 12.3 回归与人工验收

运行现有局域网互动、聊天、设置、主应用、桌宠窗口和下班提醒测试。人工验收时：

1. 在当前机器重新枚举接口，确认有线地址 `192.168.101.14/24` 使用 `192.168.101.255` 广播。
2. 若 WLAN 已连接并取得正常 IPv4，确认有线与 WLAN 的广播地址都收到发送。
3. 使用一个同广播域设备和一个可单播互通的其他子网设备，验证自动发现与保存后重连。
4. 验证加入/退出状态在互动页面快速更新。
5. 验证接收方只有桌宠所在屏幕闪烁，其他屏幕不受影响。
6. 验证发送方看到真实确认汇总，未确认设备不计入已送达。

## 13. 验收标准

- 手动 IP 验证成功的伙伴在应用重启后自动重连，除非地址变化、设备离线或网络/防火墙阻断。
- 有效多网卡分别发送定向广播，不再只依赖系统为 `255.255.255.255` 选择的单一路由。
- 所有新版客户端显示同一个固定“局域网预警组”，且每台设备只能控制自己的加入状态。
- 旧客户端不显示预警组、不接收预警组消息，但原有局域网能力不回归。
- 普通局域网群聊与预警组群聊具有不同收件范围和独立会话记录。
- 右键预警只向当前在线、兼容且已加入的其他成员发送，并在二次确认后执行。
- 接收方在桌宠所在屏幕看到约 1.5 秒、3 次峰值的红色半透明警示和发送者昵称，不抢焦点、不拦截鼠标、不播放声音。
- 重试数据包不重复闪屏，发送结果以确认包为准，频繁发送受到限制。
- 伙伴数据与预警组状态保持解耦；伙伴记录中不存在预警成员字段。
