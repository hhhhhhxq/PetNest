# Codex 子代理未读过滤设计

## 问题

Codex Desktop 会把顶层任务和它创建的子代理任务分别加入全局未读列表。PetNest 当前把每个新增未读 ID 都转换为一个 `ThreadUnread` 事件，因此一个顶层任务启动 23 个直接子代理和 2 个嵌套子代理时，会错误显示“25 个待查看”。

## 目标

- 子代理任务完成不增加 PetNest 的“待查看”数量。
- 顶层任务完成后仍产生一个待查看提示。
- 打开顶层任务后，已有提示按现有逻辑清除。
- 不读取对话正文，只使用 Codex 本地状态数据库中的父子关系。
- 数据库短暂繁忙、尚未写入或 schema 不兼容时，不把未知任务猜成顶层任务。

## 方案比较

1. 继续逐个计算全部未读 ID：实现不变，但子代理驱动任务会严重误报。
2. 把子代理未读折叠到顶层任务：数量看似正确，但第一个子代理完成时主任务可能仍在运行，会过早显示“1 个待查看”。
3. 过滤子代理，只让已确认的顶层任务产生提示：能同时保证数量和提示时机正确，采用此方案。

## 设计

### 任务关系查询

在 `CodexThreadIndex` 增加批量分类接口。接口以只读方式查询 `threads` 和 `thread_spawn_edges`：

- 出现在 `thread_spawn_edges.child_thread_id` 中的 ID 分类为子代理。
- 存在于 `threads.id` 且未出现在子代理边中的 ID 分类为顶层任务。
- 数据库不可读、缺少所需表或 ID 尚未写入数据库时分类为未知。

查询继续沿用现有安全约束：仅访问 Codex home 内通过路径校验的 `state_*.sqlite`，使用 SQLite 只读 URI、`PRAGMA query_only=ON`、短超时和有限批量参数。

### 未读事件处理

`CodexSessionLogWatcher` 对达到稳定时间的新未读 ID 批量分类：

- 顶层任务：发出一次 `ThreadUnread`，并加入已确认集合。
- 子代理：从待判定集合移除，不发事件。
- 未知：继续留在待判定集合，后续轮询重试；不发事件。

只有曾发出 `ThreadUnread` 的顶层任务在移出 Codex 未读列表时才发出 `ThreadRead`。因此被忽略的子代理不会产生多余的清除事件。

### 降级行为

数据库短暂繁忙或 Codex 尚未写入任务关系时，PetNest 延后未读提示并持续重试。若当前 Codex 版本没有可识别的任务关系 schema，则不根据无法分类的 ID 产生待查看气泡，以避免把大量子代理误报给用户；working/review 动画的日志监听不受影响。

## 测试

- 批量分类能区分顶层任务、直接子代理和嵌套子代理。
- 25 个子代理未读不会产生任何 `ThreadUnread`。
- 顶层任务随后未读时只产生一个 `ThreadUnread`。
- 未知 ID 不会立即产生提示；数据库关系可用后可在后续轮询正确分类。
- 数据库不可用或 schema 不兼容时不产生误报。
- 顶层任务已确认后，从未读列表移除仍产生对应的 `ThreadRead`。
